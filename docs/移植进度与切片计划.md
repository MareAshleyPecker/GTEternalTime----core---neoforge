## 五、每片的固定验证流程

1. **强制重编**（先删 Kotlin 产物，避免增量假绿）：
   `Remove-Item -Recurse -Force build\classes\kotlin\main; .\gradlew.bat classes --console=plain`
   唯一允许残留的警告：`AdvancedTerminalBuilder.kt:286 Condition is always 'true'`（故意的 AE 桩）。
   ⚠️ **本仓库的构建缓存坑**：上面这条命令会**间歇性**出现 `compileKotlin FROM-CACHE/UP-TO-DATE` 但一个 class 都没恢复，
   紧接着 `compileJava` 报「找不到符号」（`GTETSCore` 之类），看着像代码错了、其实是缓存假绿。
   恢复办法：`.\gradlew.bat compileKotlin --rerun-tasks --no-build-cache --console=plain`（或 `clean classes --rerun-tasks`）。
   ⚠️ 但**别为此跑 `gradlew clean`**：它会把整个 `build\` 连同 client 的运行参数一起删掉，之后从 IDE / 启动脚本
   启动客户端会报 `Error: could not open '...\build\moddev\clientRunVmArgs.txt'`。
   恢复办法：`.\gradlew.bat prepareClientRun`（`gradlew runClient` 也会自己依赖这个任务；`runData` 只重建 data 那一套参数）。
   ⚠️ **`compileKotlin` 不编译 Java**，而 `compileJava` 同样可能 `UP-TO-DATE`/`FROM-CACHE` ⇒ **凡是改了 Java↔Kotlin
   的交叉签名（mixin 调 Kotlin 的 `@JvmStatic`、Kotlin 实现 Java 接口），必须另跑一次
   `.\gradlew.bat compileJava --rerun-tasks --no-build-cache --console=plain`**。
   实例：`MultiblockPreviewWidgetMixin` 调 `PreviewControls.attach(..., width)`，而 Kotlin 侧签名早已是
   `attach(..., schemaWidth, schemaHeight)` —— 只跑 `compileKotlin` 一直是绿的，直到某次 `compileJava` 真跑才炸。
2. 动过 datagen 就 `.\gradlew.bat runData --console=plain` 跑**两次**，第二次应无新增写入。
3. `.\gradlew.bat runClient` 进游戏实测：创造页里能看到新条目、JEI/EMI 里配方对、结构能成型。
4. 小步提交 + 推送（一片一次提交，信息写清「做了什么 + 为什么」）。

## 七、LDLib2 迁移（高级终端 UI，从 MUI 搬到 LDLib2）

**动机**：LDLib2 的界面可以用 **XML + stylesheet** 写（`UI.of(Document)` / `XmlUtils.loadXml(ResourceLocation)` 直接从资源加载，
仓库根还有 `ldlib2-ui.xsd` 给 IDE 校验），带样式表与布局系统；后续像「神锻」那种有科技树的机器 UI 也走这条路比 MUI 顺手。

**已核实的事实**（LDLib2 源码本地检出：`D:\java\GTEternalTime -- core\gittmp\LDLib2`，版本 2.2.41 / MC 1.21.1 / group `com.lowdragmc.ldlib2`）：

| 需求 | LDLib2 对应物 | 位置 |
|---|---|---|
| 手持物品开界面 | `HeldItemUIMenuType.openUI(ServerPlayer, InteractionHand)` + 物品实现 `HeldItemUIMenuType.HeldItemUI` | `gui\factory\HeldItemUIMenuType.java` |
| 界面容器/菜单/屏幕 | `ModularUI` / `ModularUIContainerMenu` / `ModularUIScreen` / `IModularUIHolder` | `gui\holder` |
| XML 界面 | `UI.of(Document)`（`<root>` + `<style>` + `<stylesheet>`），`XmlUtils.loadXml(ResourceLocation)` | `gui\ui\UI.java:69`、`utils\XmlUtils.java:63` |
| Kotlin DSL（不想写 XML 时） | `UI.dsl.kt` / `UIElement.dsl.kt` | `gui\ui` |
| 同步 | `gui\sync` + `syncdata` 两套 | `gui\sync`、`syncdata` |

**依赖**：`implementation "com.lowdragmc.ldlib2:ldlib2-neoforge-1.21.1:2.2.41:all"`（仓库 `maven.firstdark.dev/snapshots`，build.gradle 里已有该仓库）。
**依赖已落到本机 Gradle 缓存**（本工程早期短暂加过它，`D:\.gradle\caches\modules-2\files-2.1\com.lowdragmc.ldlib2\ldlib2-neoforge-1.21.1\2.2.41\` 里有 `-all.jar` 与 `-sources.jar`），
所以 S1 的依赖解析不是风险点，离线也能过。
**代价**：GTM 8.0.0 已彻底弃用 LDLib/LDLib2（源码里 0 处引用），所以它**不再是 gtceu 捎带的库**，会变成 GTET 的**必装前置**
（MUI 相反，是 gtceu jarJar 自带、零安装）。裁决：先按**必装**做（mods.toml 里 mandatory），要改成 jarJar 内嵌是后面一行的事。
**MUI 不能删**：GTM 自己的机器 UI 还在 MUI 上，两套界面库共存。

**分工裁决（用户已确认）**：**面向 GTM 的机器 UI 留在 MUI** —— 复用 GTM 的主题/贴图/JEI 配方页，零安装、
风格与 GTM 一致，机器界面还能直接抄 GTM 的；**GTET 自己的大面板走 LDLib2 XML** —— 高级终端、以后的科技树类机器、
各类编辑器这类「重交互、会反复改版」的界面才吃得到 XML + 样式表 + 数据绑定的红利（LDLib2 还自带节点图工具包，科技树方向只有它有现成积木）。
不是二选一，是按界面用途分两条路。**先做 S1 冒烟**：共存没问题再投终端重写；共存炸了就整条放弃，别写完 600 行才发现。

**⚠️ 最大的结构性变化**：LDLib2 的手持物品判定是 **`heldItem.getItem() instanceof HeldItemUI`（接口在 Item 实例上）**，
不是老工程 LDLib1 那套「`ComponentItem` 的某个组件实现 holder 接口、工厂去问组件」。所以终端物品要**自带一个 Item 子类**：
`class AdvancedTerminalItem(...) : ComponentItem(...), HeldItemUIMenuType.HeldItemUI`（组件照旧挂 `TooltipBehavior` 等），
注册处把 `::ComponentItem` 换成 `::AdvancedTerminalItem`。

**切片步骤**：

1. **S1 依赖与冒烟**：加依赖 + mods.toml 声明 + 一个最小的 `HeldItemUI`（右键开空界面）—— 验依赖能解析、与 MUI 共存不冲突、菜单开得起来。
2. **S2 数据/UI 解耦**：确认 `TerminalSettings` / `AdvancedTerminalSettings` / `TerminalItemSource` / `StructureBuildPlanner`
   里没有残留的 MUI 类型，把还在 `AdvancedTerminalPanel` 里的业务逻辑下沉成与界面库无关的 controller。
3. **S3 UI 重建（XML 优先）**：XML 放 `assets/gtetscore/ldlib2/terminal.xml`（照 `ldlib2-ui.xsd` 写），
   `UI.of(XmlUtils.loadXml(id))` → `ModularUI.of(ui)`；结构列表 / 预览 / 参数这些动态部分由 controller 绑数据。
   **⚠️ 界面要想还能用 LDLib2 自带的编辑器改，就必须是 XML**：编辑器只认 `.xml` 项目文件（默认根目录
   `<游戏目录>/ldlib2/assets`，dev 环境就是 `run/ldlib2/assets`），代码搭的 `UIElement` 树**没有导出通道**
   （`UIElement.saveXml` 是 `private` 且无调用点）。编辑流程：把界面 XML 拷进那个目录用编辑器改，改完拷回
   `src/main/resources/assets/gtetscore/`；动态部分（数据绑定 / 自定义元素）留在代码里，自定义元素在 LDLib2 注册表
   注册后会出现在编辑器元素面板里。
4. **S4 切换与清理**：换成 `AdvancedTerminalItem` 的 `HeldItemUI` 路径，删掉 MUI 面板与 `IItemUIHolder` 那条组件路径。

- **注入点（先前的判断已被实现方纠正，以此为准）**：`MachineUIPanelBuilder` **没有分页 API**
  （public 成员只有 drawGTLogo / attachInventory / addTitleBar / addTraitConfigurators / addDefaultConfigurators /
  left·rightConfigurators / mainContents / build），`IMuiMachine` 界面上「右侧那排」是 `MachineUIPanel.rightConfiguratorPanel`
  这一列按钮（电源 / void / batch / 自动输出），真正的分页是**每台机器自己在 `mainContents` 里**搭的
  `PagedWidget`+`PageButton`，外部插不进去。
  ⇒ 做法：`@Mixin(MachineUIPanelBuilder.class)` + `@Inject(method="build", at=@At("RETURN"))`
  （`build` 是 `IMuiMachine.buildUI` 的收口调用，所有走默认路径的机器都过它），拿到 `MachineUIPanel` 后
  **往 `panel.getRightConfiguratorPanel()` 加一个开页按钮**（先例 `LargeMinerMachine.java:207-222`），
  再把配置页作为 panel 的直接子 widget、默认 disabled、由按钮切换显示。
  （少数走 `MachineDefinition.getUI()` 自定义 `PanelFactory` 的机器覆盖不到，先不管。）
- 3D 渲染复用 `integration\recipeviewer\widgets\MultiblockPreviewWidget` + `client\renderer\PatternPreviewRenderer`
  （GTM 自己的 `TerminalBehavior:135` 就是这么用的）：拿机器自身的 blockstate 搭一个 1 格 schema 渲染，六个面可点。
- 数据层直接用 `AutoOutputTrait` 的 `get/setItemOutputDirection` / `get/setFluidOutputDirection` /
  `setAutoOutputItems` / `setAutoOutputFluids`；开关按钮复用 `GTMuiWidgets.createAutoOutput*Button`。
- **S1**：页面能开、3D 单方块预览能转、点面能把该面设成 item/fluid 输出（当场能看到 `MachineModel` 的覆盖贴图变化）。
- **S2**：盖子的方向配置、输入输出标记、与老 1.20.1 手感对齐（左键 item / 右键 fluid 那套）。（S1 落地后单独排。）
